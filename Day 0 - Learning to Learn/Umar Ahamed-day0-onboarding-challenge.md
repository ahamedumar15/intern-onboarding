# Deliverable 02: Feynman Check


### Day 0

- Today I learned about the onboarding process. I think of onboarding like the first day at a new school. Before starting classes, you need to know where everything is, who to talk to, and what is expected from you. In the same way, onboarding helps new team members understand the company, the people, and the way work is done. If this process is not done properly, people can become confused about their responsibilities and take longer to start contributing effectively.

### Day 1 

- Today I learned that software requirements are like a plan before starting any project. Everyone needs to agree on what should be built before development begins. It's similar to planning a house before construction starts. If the plan is not clear, people can have different ideas about what needs to be done. In software projects, unclear requirements can cause misunderstandings, mistakes, and extra work later on.

### Day 2 

- Today I learned about C4 Context Diagrams. I think of it as a simple picture that shows the system and the things connected to it. It's similar to a map that shows a place and the important locations around it. It helps us understand who uses the system, what external services interact with it, and where the system boundaries are. Without this, teams can become confused about what is part of the system and what is handled by external services.

### Day 3 

- Today I learned about requirement ambiguity. This happens when a requirement can be understood in different ways by different people. It's like telling someone to meet at a "large building" without saying exactly which one. Everyone might think of a different place. In software projects, this can lead to developers, testers, and stakeholders having different expectations. Finding and clarifying these ambiguous areas early can help avoid confusion and reduce rework later.
